# 阶段 13：筑基道、金丹道天骄判定接线修复

## 1. 用户现象

练气圆满选择筑基之道、筑基圆满选择金丹之道时，突破页和突破开始提示始终显示路线的固定基础雷数、固定基础伤害，看不到当前天骄档位产生的倍率变化。

## 2. 根因

- 服务端实际运行链路已经调用 `TribulationScalingHelper.scaleSpec`，`TribulationSession` 也保存了启动时天骄档位和缩放后的最终劫谱。
- `CultivationScreen.breakthroughHint` 对筑基道和金丹道建立了两个提前返回的专用分支，这两个分支直接显示路线基础值，绕过了天骄缩放。
- `RequestBreakthroughPacket` 虽然把缩放后的劫谱传给 `TribulationHandler`，但开始提示仍读取缩放前的 `waves`、`damage` 局部变量。
- 因此形成“实际运行已经缩放，界面和提示仍显示旧值”的双口径状态。

## 3. 修复契约

1. 路线枚举只提供未缩放基础劫谱。
2. 客户端预览和服务端启动统一调用 `TribulationScalingHelper.scaleSpec`。
3. 服务端只创建一份 `finalSpec`；Session、开始提示均读取该对象。
4. 筑基道/金丹道预览同时显示当前天骄档位、最终雷数和最终单雷伤害。
5. `scaleSpec(TribulationTier, TribulationSpec)` 作为纯计算入口，十档天骄共用同一算法。

## 4. 红灯与回归测试

修复前连续两次运行：

```text

筑基道预览必须读取天骄缩放后的最终劫谱
```

修复后：

- `StageOnePolicyTest.daoRoutePreviewAndStartMessageUseTheSameTianjiaoScaledSpecAsRuntime` 通过；
- `DaoRouteTianjiaoScalingTest.everyTribulatingFoundationDaoUsesEveryTianjiaoTier` 通过；
- `DaoRouteTianjiaoScalingTest.everyGoldenCoreDaoUsesEveryTianjiaoTier` 通过。

行为测试覆盖地道/天道筑基、四种金丹道与全部十档天骄的组合。
